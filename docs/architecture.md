# Foundation integration boundaries

BuildEstate uses Angular standalone routes and strict generated API types, Go standard HTTP handlers/application services and persistent SQLite. The composition root explicitly mounts each feature with `RegisterRoutes(mux, dependencies)`; packages never self-register through init side effects. Unimplemented feature slots deny access or report unavailable, never simulated success.

`backend/internal/contracts` belongs to module `buildestate/backend` and imports only the Go standard library. Concrete access, platform, audit, document, finance and sales packages depend inward on these interfaces, not on one another's transport packages. `Dependencies` supplies `DB *sql.DB`, injectable `Clock`, `Policy`, `Transactions`, `Audit`, `Evidence`, `Costs`, `Booking` and `Projections`. Nil services are unavailable, not allow-all implementations. No concrete authentication is supplied here.

The transport bounds/decodes inputs and uses generated wire contracts; application services own policy/lifecycles and transactions; repositories receive an existing `Transaction`. Its interface deliberately has no commit/rollback methods. `Transactions.WithinWrite` owns the serialized immediate transaction. It includes current access and record-version checks, idempotency identity/digest, business effects and append-only audit. Hashing passwords, uploading files and rendering exports take place outside the write lock. A service cannot commit its business state separately from audit or replay evidence.

`AuditWriter` receives allowlisted safe changes; `EvidenceValidator` validates completed typed-parent evidence in the current project. `CostRecognition` preserves one economic source for linked expenses and bills, excluding payment cash from costs. `BookingFinance` derives booking balances from attributed posted allocations and validates current evidence/refund caps. `ReadProjections` returns named narrow structs rather than arbitrary maps, so cross-domain selectors and summaries do not expose entire confidential records. Every read implementation must apply the trusted actor/access revision and authorized project/record scope before aggregation and pagination.

The API compatibility boundary is `/api/v1`. Contract authoring, composition, validation, generated DTOs and availability semantics are documented in `docs/api/README.md`. Contract validation does not mean business features are implemented or tested. Backend adapters and Angular services must use matching error/envelope/nullability/exact-decimal rules. UI effects are post-commit invalidation hints; reloading always fetches server truth.

The platform implements persistent connections, foreign keys on every connection, WAL, full synchronous mode, five-second busy timeout, one serialized writer and four query-only readers. `Dependencies.DB` is the writer and `Dependencies.ReadDB` is the bounded reader pool; repositories performing atomic state changes must use the writer transaction. The server composition root supplies both explicitly. This document describes interfaces and architecture, not verification of feature implementations.
